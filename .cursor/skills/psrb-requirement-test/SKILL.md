# PSRB 需求测试

三个仓库：`csl-new-server`、`csl-new-front`（前台）、`csl-new-ui`（后台）。
需求文档优先，代码只用来定位页面、接口和字段。需求和代码都没写的反向情况也要写用例。

## 固定要求

1. 跑脚本的时候记得打开浏览器，用户要看。使用 `npx playwright test --headed`，失败时保持浏览器不关。
2. 报错要总结，并说出和需求文档哪里不一致。每条失败写：需求原文、实际结果、涉及项目/记录编号、前台还是后台、对应接口。
3. 生成测试用例时，根据需求文档，结合三个仓库里的对应功能生成。以需求文档优先，代码为辅。需求和代码里面都没有的反向逻辑也要考虑到。

## 四类必测

每条需求都要先问：未开启会不会误发、筛选和列表是不是同一批、前后台是不是同一个数、不该看的人是不是真的看不到。

### 1. 节点未开启不做后续动作

节点没有扫描记录就是未开启。未开启不得自动指派，不得给该节点的人发指派邮件，也不得把上传记录标成已扫描。

反例：项目只开了渗透，基线仍是未开启，却给基线负责人发了邮件。

用例至少包含：只开其中一个节点；其余节点保持未开启；核对指派字段、邮件收件人、上传记录状态。

### 2. 筛选和列表用同一套口径

筛选项选中的状态，必须和列表单元格的展示状态是同一次计算。不能拿任意一条历史扫描日志的原始状态去筛。

反例：只筛「基线安全 - 漏洞待修复」，结果里出现「待人工审核」。

每个节点、每个筛选项都要单独造一条数据再筛一次。断言列表状态、条数、导出结果和接口返回一致。

### 3. 前后台同一份数据

前台和后台都展示的数字、列表、详情，用同一个项目核对。对不上就是缺陷。

反例：多分支扫描后，前台漏洞数是后台的 3 倍。

核对项目编号、节点、批次或分支、漏洞条数、状态。历史批次、别的分支、别的节点不能算进当前展示。

### 4. 不能看的人确实不能看

每个权限点除了正向账号，再选一个不该看到的账号。用这个账号打开菜单、列表、详情、导出、接口。

断言：菜单不可见，或列表没有这条数据，直接调接口也被拒绝。不能只验证「有权限的人能看到」。

## 生成用例的顺序

1. 摘需求里的角色、节点、状态、邮件、筛选、前后台页面。
2. 到三个仓库里找到对应接口和页面，只补充字段和入口，不改需求含义。
3. 为上面四个维度各写正向和反向。
4. 再补需求和代码都没写、但会踩坑的反向：空数据、最新包已扫描而旧包未扫描、只开一个节点、一个分支失败、无权限、前后台刷新后数字仍一致。
5. 用例写清造数、操作、期望、失败时要对照的需求句子。

## 还要核对

- 同一条业务规则只算一次。列表、筛选、详情条数、导出、邮件收件人必须来自同一批、同一个节点。多分支只认该分支当前该展示的记录，历史扫描不能累加。
- 状态没变成「已发生」之前，副作用不能先发生。未开启不指派、不发信；没写出扫描日志，上传记录保持未扫描。扫描失败如果已经有日志，上传记录才算已扫描。
- 造数要能区分对错。至少准备「只开一个节点」「同一分支一旧一新」「前后台都能打开的同一个项目」「一个有权限账号和一个无权限账号」。不要只用一条全通过的数据。
- 选包规则单独断言。推送看的是该分支最新的包，并且它还没扫过。最新包已扫描时，更早的未扫描包不能被补推。

## 脚本

- 脚本放在 `playwright/tests/<需求号>/`，造数和账号沿用现有 `fixtures`、`utils/accounts.js`。
- 页面脚本必须 `--headed`。
- 断言同时看页面和接口。前后台各读一次同一个项目。
- 筛选用例按节点和状态拆开，不要只抽一条代表全部。
- 失败输出必须带需求不一致说明，不能只抛 Playwright 堆栈。
