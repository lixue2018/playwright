# 01 · 节点闸道规则（公共）

> **适用范围**：所有 PSRB 项目节点相关测试（人工用例、E2E、造数、datagen）。  
> **代码入口**：`utils/node-order.js`（闸道）· `utils/rules.js`（申请暂停禁态，可与下文章节对照）  
> **服务端依据**：`DetectionReviewManager.getCanUpdate` + `successList`（各节点 audit 先调）  
> **口诀**：先测左边 → 本闸道测完再审过 → 再测右边。  
> **审批口诀**：已通过类终态不能再审；**不通过可以二次审**；暂停只能重启，不能直接审通过/不通过。

---

## 1. 为什么要分闸道

左侧节点一旦进入「通过 / 通过遗留 / 免审 / 免审遗留 / 不适用」等**不可再审终态**，中间态（排队中、待审核、审核中、待提交、材料待更新等）往往消失，且后台节点审批会被拦住。  
若一上来把左侧全审过，再回头测右侧，**测不全**。

因此：**同一闸道内先做完要测的内容（含前台提交材料、后台审核），再统一审到业务终态，解锁下一闸道。**

> **造数 / 自动化补充**：终态不可逆时如何分项目、分节点角色（`pause_ok` / `paused` / `forbid` / `close`），见  
> [`docs/4834/造数状态池与用例消耗.md`](../4834/造数状态池与用例消耗.md)。默认造数**不要**为挤出下一节点而免审左侧。

---

## 2. 闸道定义（固定）

| 闸道 | 节点（导航从左到右） | 本闸道可测内容（示例） | 本闸道测完后才允许 |
| --- | --- | --- | --- |
| **G0** | 基本信息 | 基本信息相关：等级/字段、前台提交、后台审核、申请暂停等（视需求） | 将**基本信息审批通过** |
| **G1** | 架构审核、数据安全、隐私安全、源代码安全（**4**） | 各节点：前台提交文件/材料 → 后台审核；可申请暂停等中间态用例 | 将本闸道 **4 个节点全部**审到通过（或免审 / 不适用等业务终态） |
| **G2** | 开源组件安全、基线安全、渗透测试、AI安全、网络基础设施审核（**5**） | 同上：前台提交 → 后台审核；暂停/恢复等 | 将本闸道 **5 个节点全部**审到通过（或终态） |
| **G3** | 终审 | 前台提交 / 申请关闭 → 后台审核；终审**无**申请暂停 | — |

```text
G0 基本信息
    │  测完（含前台提交、后台审核）→ 审批通过
    ▼
G1 架构 / 数据 / 隐私 / 源码
    │  测完（含前台提交、后台审核）→ 全部审批通过（或免审等）
    ▼
G2 开源 / 基线 / 渗透 / AI / 基建
    │  测完（含前台提交、后台审核）→ 全部审批通过（或终态）
    ▼
G3 终审
       才能测（含前台提交、后台审核 / 申请关闭）
```

### 解锁条件（硬约束）

1. **未过 G0**：不要测依赖「基本信息已通过」才开启的 G1 完整链路。  
2. **未过 G1**：不要当作 G2 已完整开启去测 G2 的「审核中 / 待提交」等态（G2 在未开闸前可测「未开启」禁态对照）。  
3. **未过 G2**：不要测终审关闭主链路（除非独立专用项目且文档写明例外）。  
4. **禁止**：为赶进度先把整闸道审死，再回头找中间态。

## 3. 后台「节点审批」能否再审（全节点同一套）

> 与闸道正交：**每个安全大节点**（含基本信息、终审）走同一套 `getCanUpdate`；差别只在「测到哪一闸、终审关闭是否锁全项目」。  
> **不要**和前台「申请暂停」禁态混用（见 §3.4）。

### 3.1 结论（先看这三条）

1. 状态为「审核通过」等 **successList / 完成类终态** → **不能再审**（文案多为「当前节点已通过，无法修改」；免审/不适用可能文案不同，效果一样）。  
2. 另拦：**未开启 (103)**、**审核暂停 (99)**、**已关闭 (11)**；终审关闭后整项目「项目已关闭，无法修改」。  
3. **审批不通过 (3) 反而可以二次审批**；其余中间态也可继续审。

业务上的「完成态」`getInOver` **只认** `2`、`21`（通过 / 通过遗留）；但**拦审批**的范围比这更大（含免审、不适用等，见下表）。

### 3.2 按状态：拦 / 不拦

#### A. successList —— 已通过类，禁止再审

| 状态码 | 含义 | 节点审批 |
| --- | --- | --- |
| 2 | 审核通过 | ❌ 不能再审 |
| 21 | 审批通过（遗留漏洞） | ❌ |
| 100 | 不适用 | ❌（常先被单独拦，文案可能不同） |
| 101 | 免审 | ❌（同上） |
| 102 | 免审（遗留漏洞） | ❌（同上） |
| 5 | 只做黑白盒（历史态） | ❌ |
| 6 | 只做隐私（历史态） | ❌ |

命中后典型抛错：`当前节点已通过，无法修改.`

#### B. 其它也会拦住节点审批的状态

| 状态码 | 含义 | 行为 |
| --- | --- | --- |
| 103 | 未开启 | ❌ `当前节点未开启!` |
| 99 | 审核暂停 | ❌ 不能直接审「通过/不通过」；前端只给「审核重启」（改回审核中=1） |
| 11 | 已关闭 | ❌ 多在终审关闭后；终审已关闭 → 整项目 `项目已关闭，无法修改.` |

终审若已是 successList / 暂停 / 关闭，**其它节点也往往改不了**（项目级锁）。

#### C. 反而允许再审

| 状态码 | 含义 | 节点审批 |
| --- | --- | --- |
| 3 | 审批不通过 | ✅ **可二次审批**（终审注释口径：未通过可二次审，通过了不允许） |
| 1 | 审核中 | ✅ |
| 4 | 待提交 | ✅ |
| 17 | 待审批 | ✅ |
| 18 | 漏洞待修复 | ✅ |
| 19 | 材料待更新 | ✅ |
| 88 | 排队中 | ✅ |
| （其它非上表禁态的中间态） | — | ✅ 以接口为准 |

### 3.3 落到每个节点（勾选用）

> 规则对下列每个节点**相同**；测时按闸道推进，在「可再审」态做完用例再点通过/免审。

| 闸道 | 节点 | 可再审时测什么 | 一旦变成 2/21/100/101/102… |
| --- | --- | --- | --- |
| G0 | 基本信息 | 前台提交、后台节点审批、（若有）申请暂停链路 | ❌ 不能再走节点审批改结果；中间态用例结束 |
| G1 | 架构审核 | 前台提交文件/材料 → 后台审批；暂停/恢复等 | 同上 |
| G1 | 数据安全 | 同上 | 同上 |
| G1 | 隐私安全 | 同上 | 同上 |
| G1 | 源代码安全 | 同上 | 同上 |
| G2 | 开源组件安全 | 同上 | 同上 |
| G2 | 基线安全 | 同上 | 同上 |
| G2 | 渗透测试 | 同上 | 同上 |
| G2 | AI安全 | 同上 | 同上 |
| G2 | 网络基础设施审核 | 同上（可能长期不适用=100，则本身就不能再审） | 同上 |
| G3 | 终审 | 前台提交 / 申请关闭 → 后台审核；**无**申请暂停 | 通过类终态不可再审；关闭(11)锁项目 |

**单节点验收口径（每个节点都用这张纸）**：

```text
当前态 ∈ {1,3,4,17,18,19,88,…中间态}
  → 后台「节点审批」应可打开并可提交（含：3 不通过 → 二次审）

当前态 ∈ {2,21,100,101,102,5,6}
  → 应拦截：当前节点已通过，无法修改（或免审/不适用等价文案）

当前态 = 103 → 未开启，不可审
当前态 = 99  → 仅「审核重启」，不可直接通过/不通过
当前态 = 11  → 已关闭；若终审关闭则项目级不可改
```

### 3.4 别和前台「申请暂停」混了

| 能力 | 依据 | 禁态（不可点/不可提交） |
| --- | --- | --- |
| **后台节点审批** | `getCanUpdate` + `successList` | 2 / 21 / 100 / 101 / 102 / 5 / 6；另拦 103 / 99 / 11 |
| **前台申请暂停** | `PauseNodeProcessRules` | **103 / 101 / 102 / 2 / 21 / 99 / 11**（**不含 100**） |

例：节点为「不适用(100)」→ 不能再节点审批；是否还能申请暂停，以暂停规则为准（禁态表不含 100，但产品若未开申请入口另论）。用例里必须写清测的是哪条能力。

## 4. 闸道内怎么测（少换登录）

同一闸道内，建议按导航从左到右：

1. 接口人：前台该节点该测的（提交文件、申请暂停/恢复/关闭等）  
2. 本节点审核人：后台该测的（节点审批、暂停审核、恢复审核等）——**仅在可再审态**操作  
3. 再换下一节点  

口诀：**一个节点测完所有可能性，再换下一节点。**  
一旦该节点已进 successList，不要再指望用「再审」把态改回来造中间样本（应另开项目或闸道内提前留样）。

闸道内节点之间**可以**并行造多个样本项目；**同一项目**推进时仍须守「测完再审过」。

## 5. 冒烟 vs 全量

| 模式 | 是否可缩短 | 说明 |
| --- | --- | --- |
| **冒烟最短** | 可以 | 造数可免审某一前置节点、只留 1 个可暂停态，跑通一条主链路 |
| **全量 / 人工回归 / 跨节点态** | **必须守闸道** | G0→G1→G2→G3；测完本闸再审过 |

造数停闸示例（4834）：

```bash
npm run prepare:4834 -- --stop-at-gate g0 :216   # 只建项，测 G0
npm run prepare:4834 -- --stop-at-gate g1 :216   # 基本信息已过，留下 G1 中间态
```

## 6. 脚本与用例必须遵守

- 新需求用例：在文档开头链到本文；状态前置写清「当前闸道 / 上一闸是否已过 / 当前态是否还可节点审批」。  
- 断言「不能再审」时：用 §3.2 successList + 103/99/11，不要只用「通过」。  
- 断言「可二次审」：优先造 **审批不通过(3)**。  
- 新 E2E / 造数：读 `utils/node-order.js`；暂停禁态对齐 `utils/rules.js` 的 `PAUSE_FORBIDDEN`。  
- datagen `--from` / `--to`：不得跳过未解锁闸道的业务含义（可技术续跑，但用例预期须标明闸道）。
