## 节点状态（测试采用 §3.1.3，见 U-001 / U-003）

| 优先级 | 界面文案 | 条件 |
|--------|----------|------|
| 1 | 未开启 | 当前文件不需要测试当前节点（需求4939相关改动） |
| 2 | 等待扫描 | 最近一次扫描周期内，所有文件都处于等待扫描 |
| 3 | 扫描中 | 任一文件已上传第三方平台，或正在获取漏洞信息 |
| 4 | 待人工审核 | 存在状态为「待处理」的漏洞 |
| 5 | 漏洞待修复 | 存在「待修复」或「待评估」 |
| 6 | 扫描通过 | 漏洞均为「已修复」「已忽略」，或漏洞数量为 0 |
| 7 | 扫描失败 | 所有文件均测评失败 |

同时命中多条时取优先级数字更小的文案。

### TC-A-ING01 项目不存在时创建并挂报告
- **层别**：L2（P0）· **fixture**：NEW01 · **A5**
- **变更前**：按项目名称查询，项目列表无该名称
- **步骤**：
  1. 传入一条 Coverity 扫描报告链接、新项目名称、接口人 itCode
  2. 后台 → DevSecOps → 项目管理，按应用名称查询
  3. 进入项目详情 → 源代码安全，查看报告区
- **预期**：
  1. **UI**：列表新增 1 条，应用名称与传入项目名称一致；接口人展示为传入人员（姓名(itCode)）
  2. **UI**：源代码安全出现 **Coverity扫描报告（扫描编号：n）** 与链接、蓝色 **查看报告**
  3. **API**：项目 id 新生成；报告关联在该 id 上
  4. **关联面**：不产生第二条同名项目
  5. **副作用**：本步不发送「获取失败」邮件

### TC-A-ING02 项目已存在时只关联文件
- **层别**：L2（P0）· **fixture**：EXIST01 · **A2/A3**
- **变更前**：记录已有项目 id、报告条数
- **步骤**：对同一项目名称再传入一条新的 Coverity 报告链接与同一接口人
- **预期**：
  1. **UI**：项目管理列表仍只有该名称 1 条；项目编号不变
  2. **UI**：源代码安全 Coverity 报告条数 +1，新链接可见
  3. **API**：项目 id 不变；新文件挂在原 id
  4. **副作用**：不新建项目

### TC-A-ING03 接口人与基本信息一致
- **层别**：L1（P0）· **fixture**：NEW01 · **O50.1**
- **步骤**：打开新建项目基本信息，核对接口人
- **预期**：

  2. **API**：接口人字段 ≡ 界面

## 功能二：多工具流程隔离

**marker**：`admin_coverity_isolate`  
**fixture**：ISO01  
**依据**：AC-2、AC-15

### Wiki / 原型展示字段

| 区域 | 原型真实文案 |

| 报告行 | **Coverity扫描报告（扫描编号：n）** |
| 按钮 | **查看报告** |

### TC-A-ISO01 处理 Coverity 漏洞不改变 Checkmarx
- **层别**：L3（P0）· **fixture**：ISO01 · **A2/A4**
- **变更前**：记录 Checkmarx 某洞状态、Coverity 某洞状态、两侧节点内计数
- **步骤**：只把一条 Coverity 漏洞从「待处理」改为「待修复」（后台去处理或等价审核）
- **预期**：
  1. **UI**：该 Coverity 洞状态为 **待修复**；Checkmarx 洞状态与变更前逐字相同
  2. **API**：Checkmarx 记录 status/id 不变；Coverity 目标洞已变
  3. **关联面**：Checkmarx 扫描报告链接与扫描编号不变
  4. **副作用**：Checkmarx 侧不新增操作记录

### TC-A-ISO02 处理 Checkmarx 不改变 Coverity
- **层别**：L2（P0）· **fixture**：ISO01 · **A3**
- **变更前**：记录 Coverity 洞状态
- **步骤**：只修改一条 Checkmarx 漏洞状态
- **预期**：
  1. **UI / API**：Coverity 漏洞状态、vulnerability_id、提交时间与变更前一致
  2. **关联面**：Coverity 报告行仍在
  3. **副作用**：Coverity 操作记录无增量

### TC-A-ISO03 复测不交叉匹配另一工具
- **层别**：L2（P0）· **fixture**：ISO01 · **AC-15**
- **步骤**：对 Coverity 按 vulnerability_id 复测；同一项目 Checkmarx 用 similarityHash 另有洞，且存在与 Coverity 相同的编号字符串
- **预期**：
  1. **UI**：Coverity 只按自己的 vulnerability_id 对旧列表；Checkmarx 只按 similarityHash 对旧库
  2. **API**：两边匹配键与状态集合互不改写
  3. **副作用**：无交叉把另一工具改成已修复或待修复

## 功能三：同一周期报告链接

**marker**：`admin_coverity_link`  
**fixture**：DEDUP01 / MULTI01  
**依据**：§3.1.2、AC-3、AC-4、U-006

### Wiki / 原型展示字段

| 区域 | 规则原文对应的可见结果 |
|------|------------------------|
| 同链接 | 只保留提交时间最近的一条去拉漏洞 |
| 不同链接 | 每个不同链接都拉漏洞 |
| 举例应拉取 | 扫描报告1（2026-09-14 09:35）、扫描报告2（2026-09-14 09:30）、扫描报告3（2026-09-14 09:30） |
| 举例不拉取 | 报告1 的两条 09:30、报告2 的 09:25 |

### TC-A-LNK01 相同链接只取时间最近的一条
- **层别**：L2（P0）· **fixture**：DEDUP01 · **A5**
- **步骤**：
  1. 同一项目、同一周期提交三次同一链接：09:30、09:30、09:35
  2. 等轮询结束，看报告与漏洞批次
- **预期**：
  1. **UI**：该链接只形成一批漏洞结果，时间对应 **2026-09-14 09:35**（或 fixture 中最晚时间）
  2. **API**：09:30 的两次提交没有独立漏洞批次
  3. **副作用**：不因重复提交发三封获取失败邮件

### TC-A-LNK02 不同链接全部获取
- **层别**：L2（P0）· **fixture**：MULTI01 · **A5**
- **步骤**：按 Wiki 举例提交六条记录（报告1×3、报告2×2、报告3×1）
- **预期**：
  1. **UI**：拉取结果覆盖报告1@09:35、报告2@09:30、报告3@09:30 三份
  2. **API**：三份链接均有漏洞结果（或明确的空结果），报告2@09:25 与报告1@09:30 无独立批次
  3. **关联面**：三份结果都挂在同一项目

### TC-A-LNK03 周期边界（人工，U-006）
- **层别**：L1（P1）· **人工验证** · 禁止 skip 计通过
- **步骤**：在实机认定的扫描周期外再提交一条旧链接，记录平台实际窗口
- **预期**：窗口内链接按 TC-A-LNK01/02；窗口外是否参与，把实机行为写回 U-006
